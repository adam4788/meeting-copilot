# Overlay lifecycle and publication contract

## Identity and retirement

- `snapshot_id` is an unguessable bridge-instance ID plus a monotonic presentation epoch. Native clicks must echo it alongside the row ID. The epoch advances on meeting/capture changes, corrected/removed question identities, authorization refresh, scope changes, and retirement. Missing/old identities are rejected; no row-only compatibility path exists.
- Swift captures the displayed identity in the button closure, not just the identity current when a delayed action runs. Before spawning a display, the bridge runs a bounded, stdin-free `--protocol-version` probe and requires `meeting-overlay/2`. Old helpers fail closed with an actionable rebuild error; no private snapshot is sent and no legacy click path is enabled.
- Each pane allocates a creation ordinal synchronously at its first render, **before** any lifecycle GET. A renderer-global coordinator survives plugin unregister/re-register and supplies one opaque ordering-domain ID plus a monotonically increasing ordinal. `/overlay/lifecycle` returns the backend epoch and current revision; HTTP `/overlay/claim` requires the epoch, domain ID (`client`), and creation ordinal (`creation`) as well as the revision. Within the bound domain the creation ordinal, not GET/POST arrival or the revision read, decides which pane is newer. A late lower/equal ordinal is rejected even if its GET was handled after a newer pane claimed. A higher ordinal may supersede despite an older revision read. Release never resets this high-water mark. Missing ordering cannot downgrade to the former revision-only claim protocol.
- The backend issues an opaque `pane` capability; desktop Start, Pause, Clear, Show, Hide, unmount, and plugin unregister carry that capability and a strictly increasing action counter. There is **no** unscoped unregister Pause. Start/Pause/Clear hold the lifecycle lock from admission through completion (including Clear's restart/failure handling). Release revokes the capability before pausing capture. Stale commands and releases cannot pause/clear the new owner, regardless of their counter size. A claim may have committed despite a lost response: failed claims are not silently retried or assigned a new identity. The error explicitly directs the user to close/reopen, creating a genuinely new lifecycle.
- Explicit Show additionally mints a display `owner`. Scope requests must echo it and a display-local scope sequence. Hide, expiry, Clear, and New meeting revoke this display owner. Hide permits a later ordered Show from the same mounted pane; Release does not.
- An unchanged scope synchronization in an unchanged captured caller context is idempotent: it does not rotate authorization, cancel work, or erase completed output. The pane suppresses the redundant post-Show effect. Actual scope changes or changes to any captured context variable (except the internal action nonce) retire pending taps, admitted work, and completed output, then rebind authorization. This deliberately treats unknown host context changes conservatively.
- Every changed selection and every scope send invalidates the last acknowledged key. Manual and automatic sync share the same sequence/owner checks; a late broad response cannot acknowledge a subsequent narrow selection. Permission changes are sent immediately, without the former debounce. Failure of the current scope send triggers an ordered, capability-bound Hide. If even Hide cannot be confirmed (for example, total transport loss), the pane explicitly reports that closure is unconfirmed rather than claiming safety; the backend lease remains the offline fail-safe.
- An ordinary capture epoch transition in the same meeting preserves completed answers, including the interval between terminal publication and worker-map cleanup. Completion is explicit state, not inferred from an empty worker map. Pending/partial work is invalidated.
- A cancelled partial is marked incomplete with a partial-result warning before the next status pump. Capture-epoch retirement checks explicit completion even after the worker has removed its request mapping. Thus an unmapped partial cannot survive pause as a completed answer.
- Clear, explicit New meeting, and switching sessions synchronously retire and detach the overlay before changing meeting state, then attempt bounded helper cleanup. Only confirmed process exit is reported as hidden. Unconfirmed cleanup retains the exact bridge for Retry hide overlay / Clear, blocks Show and capture restart, and warns that the old window may still contain meeting content. Already admitted provider calls use cooperative cancellation and cannot be retracted from an external service.
- Initial capture (no previous session) is not a meeting switch: an overlay explicitly shown before capture stays live. Successful Clear and actual meeting switches also reset local Hide/owner state immediately; reopening does not wait for the status reconciliation grace period.

## Ordering limits and non-pane API compatibility

Creation ordering is supported within **one JavaScript renderer realm per backend lifetime**. Two unrelated renderers cannot prove which pane was created first from messages delivered in arbitrary order. We do not introduce trusted wall clocks, browser storage, IP ordering, or a caller-supplied timestamp comparison across renderers. The first accepted renderer binds the backend; a different domain is rejected even after Release. A full renderer reload (unlike a plugin re-register in the same realm) therefore requires returning to the original renderer or, when other sessions are idle, closing all panes and restarting the backend. The UI reports this limitation instead of taking over. A host-wide creation authority would be needed for transparent multi-renderer handoff; that is not implemented here. Lack of `crypto.randomUUID` or counter exhaustion also fails closed. Admission can only revoke an older pane once the backend receives a newer claim; it cannot anticipate an as-yet-unreceived pane creation.

These are anti-stale lifecycle fences, **not a new authentication system**. Existing host REST authentication/authorization remains required. The domain/ordinal do not grant permissions and are not secrets; an already-authorized hostile caller can still send deliberate fresh controls. Internal watchdog, teardown, and direct MeetingState calls remain trusted. The old revision-only claim/CAS helper is retained solely for trusted internal callers/tests, not exposed as an HTTP fallback.

Non-pane clients retain the existing `/start`, `/pause`, and `/clear` request shapes **until the first pane claim in that backend lifetime**. After a claim, even if the pane releases, a missing fence returns HTTP 409 with migration guidance (malformed/mixed fields and unknown keys fail closed). This intentional restriction is necessary: an empty legitimate command is indistinguishable from an old buffered pane command. To control a shared backend without acquiring pane ownership:

1. GET `/overlay/lifecycle` under the existing host authorization.
2. Include **both** returned `revision` and `epoch` in the POST JSON, alongside ordinary Start settings if applicable. Do not include `pane` or `action` in this mode.
3. A claim/release between the lookup and command makes it stale: handle 409 and ask for renewed intent, not an automatic read/retry loop. A restart also invalidates the epoch. The token covers the pane lifecycle, not every external API client's meeting mutation; it is not a transaction log or a single-use global command sequencer.

Upgrading frontend/backend together is required for pane ownership. Revision-only HTTP claims are refused explicitly. A failed **lifecycle GET** is retryable on the next explicit user action using the same creation identity: a lookup cannot have committed ownership. Once a claim POST has been attempted, rejection, malformed reply, or transport loss is cached for that lifecycle; it is never replayed with a fresh ticket. Closing and reopening creates a strictly newer lifecycle within the same renderer. An uncertain old claim delivered after that new claim is rejected by creation order. Empty-session source changes close the local overlay UI immediately just like backend retirement; destructive-change confirmation is still shown only when retained content could be lost.

## Capture lease, Restart, and reload recovery

- After the first pane claim, **unscoped `/status` is read-only** and unscoped `/heartbeat` returns `accepted:false`. Polling by a rejected renderer, helper, or stale UI cannot keep capture alive.
- The renderer sends `/heartbeat` only with its successfully claimed `pane`. The backend validates current pane identity under `overlay_lock`, without consuming the action sequence. A superseded pane cannot renew the current lease. A heartbeat arriving after the 30-second lease deadline is rejected even before the watchdog runs; it cannot resurrect the expired lease. Explicit consented Start establishes a capture lease. Show renews only an idle display lease, never an active capture deadline. A new claim establishes pane authority only after retiring the prior capture; it does not transfer capture consent.
- A healthy owner sends heartbeats every 10 seconds. Abandoned capture stop is attempted on the first 2-second watchdog check after 30 seconds without renewal (at most **32 seconds to initiate stop**, subject to scheduler availability; actual device/process teardown can take longer). Status polling does not alter this bound. The test clock verifies the exact 32-second stop boundary; real-renderer tests verify that a legitimate owner remains live while stale/reloaded traffic cannot renew it.
- Built-in Restart retires that effect lifecycle's callbacks and heartbeats, awaits any already-attempted claim, then **awaits capability-scoped `/overlay/release`**, which pauses owned capture. It never sends legacy Pause or obtains an administrative revision as fallback. It reopens only after an accepted, stop-confirmed release (or when the lifecycle never acquired ownership). Lost/failed release or an accepted release with `stop_confirmed:false` is reported as unconfirmed; no success notice or automatic reopen is claimed. The retired pane renders recovery guidance instead of interactive controls, and its captured Assist/replay/network/clipboard callbacks are fenced. Passive status reads remain allowed. Close/reopen creates a current pane that can inspect stopping status and explicitly Retry stop. A new pane registration, newer effect lifecycle, or plugin registration superseding the waiting operation fences its UI continuation. Old commands and renders cannot remove/open newer registrations.
- **Same-renderer remount:** close/reopen the pane (or a successful built-in Restart). Creation ordering survives plugin re-registration in that JS global. The new pane can claim and Start with explicit consent; old cleanup cannot stop it.
- **Full renderer/window reload with lost cleanup:** automatic takeover is deliberately unavailable. Independent renderer UUIDs have no trustworthy creation ordering; granting a fresh GET or an expired lease takeover authority would also grant it to a stale renderer. A rejected new renderer remains read-only and cannot Pause/Clear the previous owner, but also cannot renew its capture. Return to the original owner if it still exists. Otherwise close all Meeting Copilot panes, allow abandoned capture to stop and verify the capture indicator/device is off, then restart the backend when other sessions are idle and reopen one pane. Backend restart creates a fresh epoch. This is the safe manual recovery path, not transparent reload recovery. If capture does not stop, stop the backend/device explicitly; do not treat a UI timeout as physical-stop proof.
- **Trusted backend API clients:** before any pane claim, legacy heartbeat/status renewal remains compatible. After a pane has ever claimed, deliberate administrative clients may send the exact `{revision, epoch}` from `/overlay/lifecycle` with `/heartbeat` as well as Start/Pause/Clear. Refreshing that ticket is a conscious trusted-client operation, never a renderer recovery fallback. A new pane claim/release invalidates old tickets; stale epochs, mixed pane/revision authorization, and malformed payloads do not downgrade to legacy access. GET status remains readable but cannot renew a claimed backend's lease. These cooperative fences are not authentication against a hostile authorized API client.

`lifecycle_test_backend.py` connects real plugin requests from the effect-aware JS harness to the real FastAPI router and `MeetingState` through an offline JSON-lines subprocess: no HTTP listener, microphone, network provider, or installed plugin. Audio hardware and the watchdog clock are synthetic; the tests drive the production watchdog body deterministically. The harness checks subprocess exit, stderr/background exceptions and protocol errors; Node also fails on unhandled asynchronous errors. Delayed-request and delayed-response gates cover both backend and renderer ordering. `test_lease_fencing.py` additionally verifies API migration, malformed/stale authorization, exact watchdog expiry, explicit Show recovery, and no cross-renderer takeover after expiry/release.

## Capture expiry and physical-stop uncertainty

- Every admitted Start/Pause/Clear control checks expiration under the lifecycle fence before doing privileged work. Expired Clear forgets data but never restarts audio. A valid Clear preserves the existing lease deadline; expiry during stop or restart preparation aborts restart. Show checks expiry before and after helper work; failed Show never touches the deadline. An explicit consented Start can begin a new lease only after the previous stop is confirmed.
- A newer claim retires the previous capture even if its old release is still in transport. It never inherits listening state. Old release cannot stop a newer unrelated capture. Claim stop/join holds only the lifecycle lock, not overlay/state locks; callback/heartbeat progress is regression-tested. An old helper Hide failure cannot strand the newly minted capability.
- `listening:false` means logical retirement, **not physical-stop proof**. Before the first stop attempt, `/status` exposes `stopping:true`, `capture.state:stopping`, and a warning. Late segments and answer work are fenced. `/pause` and accepted `/overlay/release` return `stop_confirmed:false` while stop is uncertain. Start is rejected while any adapter remains pending; Clear cannot replace that adapter.
- A failed stop retains the exact adapter and starts a **separate, sequence-fenced retry worker**, not the retired capture watchdog. Each explicit stop performs at most three attempts: the first immediately and two further attempts separated by two-second sleeps. A newer explicit Pause / Retry stop replaces the retry sequence; obsolete retries cannot touch a new capture. After three failures, uncertainty remains visible with recovery guidance rather than becoming a false Paused state. Current pane/revision authorization is required for manual retry; stale panes and unscoped fallback remain forbidden.
- Concrete native/macOS adapters use bounded joins/waits. A worker still alive after a bounded join remains unconfirmed. macOS process-group signal/wait failures propagate instead of being swallowed, preserve the process handle for retry, and suppress late delivery. Native shutdown already signals its event before notifying observers; tests exercise this real method even with an observer failure. The macOS slow-spawn path now reports `stopping`, not a synthetic `stopped` callback while its worker is alive.
- **Physical boundary:** retry count is bounded, not a guarantee that an arbitrary injected adapter, OS call, C-extension, or user callback can be forcibly interrupted. A hanging stop can retain the lifecycle lock; status still exposes stopping because adapter stop/join does not hold overlay/state locks. Native inference/download may outlast the join. Process exit and successful signals are local software evidence, not hardware/driver or external-service attestation. Meetily detach stops this plugin's reader, not Meetily's independent recorder. Already submitted provider requests cannot be retracted. If uncertainty persists, quit the actual capture process/recorder or revoke OS audio permissions and verify the OS/device indicator; do not infer microphone-off from pane closure, lease expiry, or `listening:false`.
- Real-method checks use an event-gated native worker and an actual harmless macOS subprocess with denied signal injection and successful retry. They do not access microphones, ScreenCaptureKit, installed runtimes, private recordings, or providers. These tests do not establish physical device shutdown or live visual acceptance.

## Overlay process shutdown uncertainty

- `stop()` invalidates publication before attempting process cleanup. Signal delivery and parent exit are not sufficient termination evidence: clearing a real launched handle requires parent exit, absence of its launch-created process group, and actual stdout EOF plus completion of any registered reader for every captured pipe (including cancelled startup). Both the protocol probe and display launch get a new session. A failed or hung TERM does not prevent an independent KILL attempt. At most one signal call per signal/process remains in flight, and retries reuse any unfinished teardown job. Status also treats an exited-but-retained parent as unknown, not stop-confirmed.
- **Conservative group cleanup:** TERM/KILL target only the owned `Popen`; group checks use `killpg(pgid, 0)` only. Concurrent `poll()`/`communicate()` can reap the leader before cleanup, so a check-then-group-signal cannot safely exclude reused IDs. No nonzero signal is sent to a remembered numeric PGID. A surviving group, denied probe, or delayed reader reports unconfirmed and retains the exact handle/group for retry; manual descendant cleanup may be necessary. A reused PGID can conservatively delay confirmation but cannot cause unrelated processes to be killed.
- **Scope limit:** group absence plus observed EOF and reader exit proves the tracked group/pipe lifecycle, not arbitrary descendant ancestry. Helpers must not daemonize or escape the launch group. An escaped descendant retaining stdout remains unconfirmed even if it emits lines after invalidation; reader-thread completion alone is not EOF. A retired reader drains without publishing and records EOF separately for its exact process. An IO error does not establish EOF. An escaped descendant retaining stdout is detected by this evidence, but one that also closes inherited pipes is outside this proof. There is no portable full-tree containment/attestation here; injected non-session test handles have only parent/reader evidence. Do not treat this as a general untrusted-process sandbox or hardware-stop guarantee.
- **EOF recovery:** pipe identity and its unset EOF event are registered under the bridge lock before child publication. A missing event for a captured pipe is unconfirmed, never success. A known reader IO/decode failure blocks direct and controller Show. Once the original reader has exited and the owned parent is gone, the serialized reaper may drain only that original retained POSIX pipe using nonblocking raw reads for at most 50ms. Only an actual zero-byte read records EOF; EAGAIN, IO errors, replacement pipes, active readers and deadlines do not. No recovery reader runs concurrently with the original reader or protocol `communicate()`. A live escaped stdout holder remains unconfirmed; after its private release and actual EOF, a later Hide can confirm. This does not extend the process-group/pipe containment boundary.
- **Protocol and click-channel health:** protocol probes capture bytes, record a successfully completed read before strict UTF-8 decoding, and reject malformed output without stranding cleanup on a closed text stream. Neither arbitrary exceptions nor a closed handle prove EOF. A timed-out probe with a live escaped stdout holder remains unconfirmed until an actual read observes EOF. An active display reader reaching normal EOF is unhealthy for both fresh and reused direct/controller Show even while its process is alive; the same EOF remains valid retirement evidence. Retired readers cannot mark a replacement lifecycle unhealthy. These are observed-health checks, not a guarantee against a helper failing after the final observation.
- The bridge caller waits at most 0.5 seconds for teardown evidence; the controller waits at most 0.8 seconds for its cleanup job (subject to scheduling). Neither wait performs buffered pipe IO. Cleanup jobs hold no lifecycle/publication locks. Clear, release and watchdog still initiate capture stop even if overlay cleanup blocks. Existing native/macOS audio and Meetily stop fences are unchanged; these overlay limits do not promise to interrupt an arbitrary audio adapter.
- Buffered stdout is closed only after confirmed parent/group exit **and** observed EOF plus completion of any reader for its captured pipe. The reaper gives the reader a bounded 50ms join, reports unconfirmed if it is still alive, and finishes its job rather than waiting forever. The bridge retains the handle and open streams for a later retry. Python cannot forcibly interrupt a hung OS/wrapper call. Such workers remain bounded in number and never publish asynchronous controller success. If permission denial persists, the window can remain visible: retry Hide / Clear or quit the actual helper and its descendants. Timeout alone never means hidden.
- Retired bridges are held in `pending_overlay`, never republished or reused. `/status`, Clear and accepted Release expose `overlay_stop_confirmed` separately from audio `stop_confirmed`. Unknown window state is `overlay_shown:null` (`shown:null` on Hide/Release), not `false`. `overlay_cleanup_error` persists across reads and failed retries; only a current cleanup caller accepting successful evidence clears it. A successful cleanup retry never restarts old capture or restores old content.
- The pane keeps Retry hide overlay available even if fresh helper capability is unavailable, retains Clear on an otherwise empty meeting, and disables new capture until cleanup succeeds. Restart will not reopen or claim success when release confirms audio but not overlay shutdown. Unmount and scope-sync cleanup also warn rather than declaring an unconfirmed window closed.
- `test_overlay_teardown.py` runs harmless Python children with real OS stdin/stdout pipes, denied and event-gated signaling, and a live blocked reader. It covers failed/repeated/successful cleanup, independent KILL, controller cleanup stalls across Clear/release/watchdog, idle lease expiry and pane handoff failures, lifecycle-lock progress, retained startup failures, and retired-bridge reuse refusal. The fixture always uses the original kill method, waits for exit, joins reader/reaper/signal workers, and closes pipes. The JS harness connects the same real-pipe probe to actual router/controller/UI requests. No native window, capture device, Meetily recorder or provider is used.

## Bounded controller liveness observation

- The controller retains one probe worker globally across process generations until the actual thread exits, including the interval after result publication. Only callers joining an unfinished probe for the **identical process object** share its result. A different process, an already published result whose worker still lives, a failed poll, or a 50ms wait timeout yields unknown. No blocking `poll()` runs on a control thread or while that worker owns lifecycle/publication/state locks; the 50ms wait is subject to scheduler availability.
- Sampling, publishing the result, and consuming it are distinct events. A child can exit after a live sample but before publication. Every consuming waiter checks that exact handle's cached `returncode`; a known integer exit contradicting the healthy sample yields **unknown**, not healthy and not cleanup-confirmed. This veto adds no worker and preserves healthy concurrent status/Start/Show sharing. A later call can obtain a new poll only after the global slot is released.
- Start's admission guards (and Show's reuse guard) also reject a ticket contradicted by a known exit at their observation boundary. They retire the bridge, then require bounded evidence for the same captured process and confirmed bridge cleanup outside publication/admission locks before permitting an empty-overlay admission. An unavailable fresh observation leaves the exact bridge pending and denies admission; an integer returncode alone never proves group/reader cleanup.
- **Precise limit:** an uncontradicted shared sample is observational evidence, not a new OS sample at publication or a lifetime guarantee. Reading cached `returncode=None` is not independent proof of liveness. The helper can exit without that exit having been recorded yet, or immediately after the last check; no guarantee over future process exit is made. Reader/epoch fencing and later observations continue to handle those cases. Thread limits and timeouts do not forcibly interrupt arbitrary OS/wrapper calls.
- `test_controller_probe_slots.py` gates a real inert child's poll **after** its live OS sample and **before** publication, reaps the child to establish `returncode=0` while reader notification is absent, then admits late status/Start/Show callers and four waiters. Healthy controls use the same gates without exiting. Additional gates cover known exit at all three Start admission boundaries with a blocked refresh, as well as the prior completed-result/actual-thread-exit boundary, mismatched handles, timeout and generation-wide cap. Audio and display adapters are synthetic; no live window, microphone or provider is exercised.

## Lock order

- Lifecycle operations: `lifecycle_lock -> overlay_lock -> bridge.lock -> state.lock` when nested. Clear enters its retirement boundary before acquiring `state.lock`.
- Admission: `overlay_lock -> bridge.lock -> state.lock`. The backend slot's row mapping is published before leaving the admission guard, so Hide can cancel every admitted slot. The bridge calls the already-guarded transport entry point; it does not recursively acquire an injected plain `Lock`.
- Delivery: `stdin_lock -> bridge.lock -> state.lock` (the last only for cancellation on failure). Never acquire stdin_lock while holding bridge.lock. Headless append is inside the same validation/publication fence.
- A real helper's `push()` only queues a snapshot; it never performs pipe IO under overlay_lock. The writer pump uses a nonblocking OS descriptor and a 100ms frame deadline while holding bridge.lock. Thus invalidation waits for bounded publication, not an unbounded TextIO write/flush. A partial/failed frame retires the lifecycle and closes the helper rather than resuming a corrupt stream.
- Capture stop/retry and claim joins hold only lifecycle_lock, never overlay/state locks. Process teardown and joins are outside bridge/stdin locks; Clear teardown is also outside overlay/state locks. Production uses real pipe descriptors. Arbitrary blocking file-like test writers are not a supported helper transport.

## Injected transport contract

Injected `assist` methods must accept `expected_generation=`. BackendTransport additionally requires the capture epoch and current-question validation. There is no fallback to an old three-argument transport: retrying without admission preconditions would weaken the security boundary. Rejections release the reservation and show a bounded error type; TypeError includes the keyword contract. Assertion failures in admission/poll workers propagate instead of being mistaken for routine rejection/unavailability.

## Autonomous overlay retirement and process inspection

- Start and Show reconcile the current **and pending** bridge before admitting new work. A live/unknown retired process remains retained and blocks capture with 409 (Show with 503); an orderly exited or already reaped helper can finish confirmed cleanup immediately, without an unnecessary extra Hide. Healthy overlays, including Show-before-first-Start, remain usable.
- Show rechecks fresh-helper liveness with a bounded probe outside lifecycle/publication locks before commit, and rejects an already observed exit at commit. Unknown probe results cannot report success. No check can promise the helper will not exit after the final observation.
- Controller process inspection runs on a dedicated worker with a 50ms caller wait budget and at most one in-flight probe per process. A stalled/throwing poll means unknown, never hidden. Repeated status/admission attempts reuse a stalled probe. No process method runs on the state-lock-owning caller; status may hold that lock for the bounded wait, not for an unbounded poll.
- Lock order remains lifecycle -> overlay -> bridge -> state. Healthy admission does not acquire the publication lock; this preserves Pause/resume progress when an admitted tap is waiting for state access. Retirement takes the ordered publication locks; cleanup waits run outside overlay/bridge/state locks. Probe workers acquire none of those locks and publish evidence only.
- Regression evidence includes an autonomous writer failure with a real retained child and denied signals; successful cleanup recovery without controller Hide; real clean child exits followed by fresh Show (retained and reaped handles); and a stalled process poll concurrent with Pause, repeated status, and denied Start. Mutation checks remove each safety fix and require assertion failures, then rerun restored production. Stale Clear-retirement and renderer unregister/Clear mutation targets were updated to current code, not weakened to accept setup errors.
- Verification: focused overlay/privacy/lifecycle suite **129 tests passed**; full `npm test` **652 Python tests, OK (3 existing skips), and 106 Node tests passed**. All three mutation scripts restored GREEN production. Swift self-test returned `overlay state tests passed`, protocol `meeting-overlay/2`.
- Residual boundary: Python cannot cancel an arbitrary stuck process wrapper. Its single daemon probe may remain until that wrapper returns; unknown visibility continues to fail closed. No helper termination, hardware shutdown, or future absence of faults is inferred from a timeout. These checks use inert children and offline adapters, not live capture or installed UI.

### Unreaped-child / shared-sample follow-up

- Reproduced RED from `cc326d8` with real inert children: `waitid(WEXITED | WNOWAIT | WNOHANG)` proved exit while `Popen.returncode` remained unset and reader notification was delayed. Admission increments a join sequence; a caller joining during OS observation forces another observation before healthy publication. Up to eight refresh attempts bound work under continuous arrivals; each caller still waits at most 50ms, subject to scheduling. Completed workers retain their global slot until actual thread exit. No observation, poll or signal runs on the lifecycle/publication caller.

Native Popen `poll()` can return `None` merely because that lock is busy, so neither it nor cached `returncode` alone establishes health. Missing APIs, wait errors, fallback lock contention, exhausted refresh attempts and timeouts return unknown. A contradicted healthy observation is not group/pipe cleanup evidence.
